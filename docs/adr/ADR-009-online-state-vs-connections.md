# ADR-009：在线状态与传输连接解耦（不建立全互联持久连接）

**Status**：Accepted
**来源**：`架构设计书.md` §3.7

## Context

全局节点数确认为 **≤ 200**。若每节点与所有其他节点维护持久 TCP 连接：

| 全局节点数 | 全网连接数 | 单节点连接数 | 单节点保活开销 |
|---|---|---|---|
| 200 | **19,900** | **199** | 约 400 KB，398 个 goroutine |

单看资源，200 节点其实扛得住。**真正的问题在心跳**：

- 199 条连接 × 每 30 s 一次心跳 ≈ 6.6 pkt/s 出站，对端也在发 → 单节点约 13 pkt/s；
- 全网 200 节点 → **约 1,300 pkt/s 的纯保活流量，零用户价值**；
- 更麻烦的是**任何一次全网抖动都变成 199 条连接同时重建** → SYN 风暴。

## Decision

把「在线状态」和「传输连接」彻底解耦：

```
在线状态（谁在线、叫什么、地址是什么）
  ← UDP ANNOUNCE 维护：无连接、无状态、成本趋零
  ← 每节点持有全量节点目录（200 条 × 约 64 B ≈ 12.8 KB）

传输连接（TCP）
  ← 按需拨号（lazy dial）：只在要发消息 / 发文件 / 群聊扇出时才建连
  ← 会话级保活：仅对当前有活跃会话的 peer 维持心跳
  ← 空闲回收：连续 5 min 无业务帧 → 正常关闭
  ← 单节点常驻连接目标：≤ 10
```

**双向拨号胜负规则**（消除连接撕裂）：若 `self.NodeID < peer.NodeID`，本方负责拨号；
否则只接受、不主动拨。HELLO 完成后若发现同 nodeID 已有 ESTABLISHED 连接，
按同一规则保留胜者、关闭负者，**且关闭前不发任何业务帧**。

## Consequences

**更好**

- 零保活流量、无 SYN 风暴；
- 发现层与连接层彻底解耦（`PeerDirectory` 与 `ConnManager` 互不依赖）；
- `Session.RTT()` 天然只在有连接时存在，正好服务滑动窗口自适应。

**更差（必须承认，并且要在 UI 上体现）**

- 给「已发现但未连接」的节点发首条消息需先建连 + 三段握手，
  首条消息延迟 +1 RTT 与一次握手（LAN < 5 ms，跨网段约 +60 ms）；
- **必须严格区分 UI 上的「节点在线」与「连接可用」两种状态**，
  否则用户看到「在线」却发不出消息会困惑。
  本仓库在 `PeerDTO` 中同时给出 `online` 与 `connected` 两个字段，
  CLI 的 `/peers` 与前端节点列表都分别显示，并有专门测试
  （`wails.TestIdleTimeoutIsNotReportedAsOffline`）保证
  「空闲回收不等于离线」不会被误报成离线。

## 不采纳的替代

- **全互联持久连接**：1,300 pkt/s 零收益开销 + SYN 风暴风险；
- **混合方案（热点长连 + 冷点按需）**：依赖「热点判定」启发式，
  出问题时难以向用户解释 —— 200 节点的规模下，纯按需已经足够，简单胜过聪明。
