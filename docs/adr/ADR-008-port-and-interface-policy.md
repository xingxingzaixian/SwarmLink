# ADR-008：端口与网卡策略交给用户显式选择

**Status**：Accepted
**来源**：`架构设计书.md` §4.5 / §7.4

## Context

- 默认端口 2425 与飞秋等同类工具冲突（目标用户很可能已装）；
- 笔记本多网卡（WiFi / Ethernet / VPN）下**自动选择必然出错**：
  向错误网卡广播、发现自己、VPN 场景全乱。

## Decision

**端口**：启动时探测占用并自动回退 `2425 → 2426 … 2434`；
实际端口写入 ANNOUNCE 供对端学习，**对端不需要配置端口**。

**网卡**：提供三档策略，不自动猜 VPN 场景：

- 「自动」（默认）：枚举 → 排除 loopback / link-local / 未 UP → 排除虚拟网卡 →
  按接口独立构造子网广播地址；
- 「指定网卡」：下拉列出物理网卡；
- 「仅显式种子」：关闭自动发现，只用种子 IP（VPN / 安全敏感环境）。

## Consequences

**更好**

- 与飞秋共存；VPN 用户可用；用户能知道「走的哪张网卡」（UI 展示接口与子网）。

**更差**

- 需要平台特定代码才能做到严格的接口绑定；UI 增加配置项。

## 实现注记（本仓库的做法）

架构书建议用 `SO_BINDTODEVICE`（Linux）/ `IP_BOUND_IF`（macOS）做接口绑定，
但那需要平台特定代码 + build tag。本仓库改用**可移植的等价手段**：
发送时把 socket 的**源地址绑定到该接口的 IP**（`net.DialUDP` 的 `LocalAddr`），
操作系统据此选择出口网卡。接收侧仍用 `0.0.0.0` 单 socket 收全部广播。

效果等价（报文从正确网卡发出、不会发到错误网卡），代价是无法强制
「只从某网卡收」——对 v1.0 的场景足够。
若后续需要严格的接口隔离（例如同时接入两套物理网络且要分别控制），
再按架构书引入平台特定 bind。

## 关键实现细节：子网广播地址

**必须**由 `IP + netmask` 计算子网广播地址（如 `192.168.1.255`），
**不要**用 `255.255.255.255`：路由器、启用 IGMP snooping 的交换机会丢弃它，
macOS 10.15+ 也默认禁止非特权进程向它发送。

`internal/adapters/net/udp/iface_test.go.ToSubnetBroadcast...` 锁定了这条规则。
