# ADR-003：群聊采用「全互联单播扇出 + 群状态 epoch 签名」

**Status**：Accepted
**来源**：`架构设计书.md` §4.6

## Context

群聊是 P0，但原设计零设计（无 group 模型、无扇出策略、无成员同步）。
无中心网络下群聊的核心难点不是 UI，而是**消息可达性**：
A 发一条消息时，B 离线、C 换了 IP、D 刚加入不知道群存在 —— 没有中心服务器仲裁。

这个决策会反向决定数据模型（`conv_id`）、消息表（`msg_id` 去重）、
协议（群消息 / 成员同步类型）与传输层（多目标扇出）。

## Decision

- v1.0 采用**全互联单播扇出**，群成员硬上限 **20 人**；
- 群状态由 owner 签名并以 `epoch` 单调递增传播：`StateSig = Sign(H(group_id|epoch|members))`；
- 成员按 NodeID 排序后参与签名，保证确定性；
- 数据模型与协议按未来切 Gossip 的形状预留（`msg_id` / `conv_id` / capability 位）；
- 同 epoch 冲突时以 owner 签名为准（取字节序较大者，各节点独立算出同一结论）。

## Consequences

**更好**

- 与「无中心」约束完全一致；实现简单；
- 成员一致性有明确仲裁规则（owner 签名）。

**更差**

- 20 人上限（写入 UI 约束）；
- 群主长期离线（> 24 h）则群进入只读 —— **不做自动选举**，把问题暴露给用户而非悄悄出错；
- **不做离线消息暂存转发**（那等价于引入弱中心），UI 必须诚实标注「N 人未送达」。

## 规模确认后的简化

全局节点数 ≤ 200 意味着群成员的现实天花板就是 200：

- 方案 A 的可用区间扩展到 ≤ 50 人；
- 方案 B（Gossip）覆盖 50~200 人，是群聊能力的**完整闭环**；
- **方案 C（软中继）永久移出路线图** —— 其触发条件是「群 > 200 人」，而全局只有 200 节点，
  这避免了为极端场景在「无中心」上做架构妥协。

## 升级路径（接缝已留）

切 Gossip 只需：加 `Hop` 字段 + `seen_cache`（LRU 去重表）+ 转发逻辑 +
`FANOUT_MODE` capability，**数据层不动**。
