# ADR-010：全量节点目录同步，不做增量 / 分页

**Status**：Accepted
**来源**：`架构设计书.md` §4.5 / §3.7

## Context

全局 200 节点的约束下，目录体积是可精确计算的：200 条 × 约 64 B ≈ **12.8 KB**。
而「增量同步」「分页拉取」「目录分片」会带来版本向量、断点续传、
乱序合并等一系列复杂度。

## Decision

节点目录以**全量快照**方式同步：

- `PEER_LIST_REQ` 携带本地 `list_epoch`；
- `PEER_LIST_RESP` 在 epoch 不同时返回**完整目录**；
- 单响应条目上限 256（覆盖全量 200 + 余量）；
- 本地目录上限 512，超出按 `last_seen` LRU 淘汰；
- 条目带 `last_seen` + TTL 300 s，过期即标记离线。

**TTL 用「本地到达时间」计，不用对端时间戳。**
节点收到条目时记 `last_heard_local = now`（本地时钟），TTL 判断只跟它比。
因此跨网段节点的时钟偏差**完全不影响正确性**，也不需要 `via` / `hop_count` /
来源标记来防环 —— 因为条目的新鲜度由接收方本地维护、不会被中转「刷新」。

> 这是必须写进代码注释的细节：实现时极易顺手拿对端 `timestamp` 去比，
> 那样一旦两台机器时钟不同步，就会出现「活着的节点被判过期」
> 或「死掉的节点永不消失」。

## Consequences

**更好**

- 实现极简（「内容没变就不回，变了就全发」）；
- 无需版本向量与增量合并；
- 12.8 KB 的传输成本在整个节点生命周期里可忽略；
- 调试时「拉一次目录就能看到全局状态」，排障成本极低。

**更差**

- 目录每次变更都要全量传播（200 节点下可忽略）；
- **若未来节点数增长到数千，此决策需推翻** ——
  这是一条「随规模而定」的决策，规模前提变了必须重新评审。

## 验证

`test/scale.TestTwentyNodesHaveFullDirectoryAndNoResidentConnections`：
20 个虚拟节点两两互相发现后，每个节点的目录恰好有 19 条，且**常驻连接数为 0**。
