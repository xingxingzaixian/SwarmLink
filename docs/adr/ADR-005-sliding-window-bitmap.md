# ADR-005：文件传输采用滑动窗口 + 周期性全量位图回传

**Status**：Accepted
**来源**：`架构设计书.md` §4.8

## Context

原设计是 stop-and-wait（每块等 ACK）：跨网段 RTT 20 ms 时吞吐被限制在
`512KB / 20ms = 25 MB/s`，而千兆网是 125 MB/s；块乱序无法利用；
位图每块落盘会拖垮 SQLite（10 GB 文件 = 20480 次写事务）。

## Decision

- 窗口 W 块在途（初始 8，`clamp(BDP/chunk, 1, 64)` 自适应）；
- 接收方每 500 ms 或每 32 块回传**全量位图**（**非**累积 ACK / SACK）；
- 位图内存维护，每 2 s 或每 256 块批量落盘一次；**并在每次回 ACK 时顺带落盘**
  （ACK 是低频事件，这样崩溃后总能从最近一次 ACK 处续传）；
- 块自带 `offset`，接收方用 `WriteAt` 乱序写入；
- `FILE_META` **始终携带全量 `chunk_hashes`**，使接收方能在任意时刻独立定位坏块；
- 校验失败**不清空位图**：逐块哈希定位坏块 → 只重传坏块 → 重新校验；
- 临时文件用 `.swarmlink.<job_id>.part`（天然免冲突、免路径注入），完成后 `os.Rename` 原子替换。

## Consequences

**更好**

- 吞吐不再受 RTT 限制；
- 乱序 / 丢包 / 重复到达由位图自动吸收，ACK 语义极简 ——
  这是「用带宽换复杂度」的最佳一笔交易（1 GB 文件的全量位图仅 256 B）；
- DB 写次数相比每块一次下降两个数量级。

**更差**

- 需要窗口管理代码；
- ACK 流量略增（可忽略）。

## 位图的二次开销陷阱

位图合并必须**按字节或**（`ChunkBitmap.OrBits`）而不是逐位遍历：
否则「ACK 次数 × 块数」会产生二次开销（50 GB 文件 = 102400 块 × 数千次 ACK）。

## 不采纳的替代

- **累积 ACK + SACK**：语义复杂，收益不明显；
- **自实现拥塞控制**：我们跑在 TCP 之上，TCP 已经在处理拥塞，
  这里的窗口只是为了填满管道。

## 验证

`test/e2e.TestFileTransferResumesAfterInterruption` 实测：4 MB / 64 块，
第一次在 100 ms 后中断（持久化了 60/64 块），第二次重发同一文件自动续传并校验通过。
