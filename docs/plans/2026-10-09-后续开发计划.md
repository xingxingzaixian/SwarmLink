# SwarmLink 后续功能开发计划

**日期**：2026-10-09（文件名沿用既有的「日期-主题」约定）
**依据**：对全仓 Go/Vue 源码 + `README.md`、`架构设计书.md`、`发现协议设计书.md`、11 条 ADR、12 份计划/设计文档的逐文件核对。本文所有判断都带出处，可直接抽查。
**范围**：短期冲刺（2–3 周）+ 版本路线（v1.1 → v2.0）
**取向**（按你的选择）：**继续加功能做大 + 工程基建与长期可维护性 + 补齐日常体验**；近期部署上线不是本计划的首要驱动，因此签名/分发排在 v1.4 而非冲刺。

---

## 0. 一页结论

**现状**：v1.0 的目标已全部落地，并且**实际交付已明显超出原范围** —— 图片/表情、托盘常驻与提示音、聊天视图软清空、离线传输 v2（等待上线 + 自动续传）、文件夹批量传输、三平台发布流水线，这些都不在原 v1.0 功能表里。

**但有三件事必须先处理，它们都不是新功能：**

| #     | 问题                                                                                                                                                                            | 性质                                                                                                                                                | 依据                                                                                                                                 |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **1** | **跨网段刷新实际是坏的**：`BumpEpoch()` 全仓无调用点 → epoch 恒为 1 → 同一个 `(本机, 种子)` 对**第二次起永远返回空目录**，直到本机重启                                          | 已确认的功能缺陷。同网段广播不受影响，所以现象隐蔽；现有 e2e 用例**结构上测不到**（它每次都用全新的 pair，恰好吃到"第 1 次"）                       | `发现协议设计书.md:412-431`、`:540-549`；`test/e2e/e2e_test.go:246-300`                                                              |
| **2** | **测试基线是红的，而且没有 CI**：`go test -tags wails ./...` 有 4 个平台相关的既有失败（Windows 上 POSIX 权限位/路径分隔符断言）；`.github/workflows/` 里**只有** `release.yml` | 地基问题。README 与 ADR 反复声称"三条红线由 CI 强制"，**目前这是一句不成立的话**（`make lint-arch` 接入 CI 的复选框至今未勾，且没有任何测试工作流） | `docs/plans/2026-10-08-folder-transfer.md:20`、`docs/superpowers/plans/2026-09-20-swarmlink-v1.md:488`、`README.md:23`、`ADR-001:35` |
| **3** | **发现层有低成本污染面**：UDP 侧不校验 `nodeID == Fingerprint(pubkey)`；`max_peers` 是死配置（目录无上限）；`interface_mode = manual` 实际等价于 `auto`                         | 安全与正确性缺口，修法都很小                                                                                                                        | `发现协议设计书.md:532-538`、`:551-553`、`:563`                                                                                      |

**排序原则**：先用 2–3 周把"已完成"变成"可信"（修正确性 + 建 CI 地基 + 补上欠下的手工验收），再按 **加密与规模化 → 体验闭环 → 批量与吞吐 → 运维分发 → v2.0 扩展** 推进。

**为什么不是先做加密**：加密是架构书 §9.1 早已选定的下一步（选项 C 的兑现点），也是本仓接缝留得最完整的一项（`Flags.ENCRYPTED`、`TypeKeyExchange 0x40`、`security.encryption` 三档），所以它值得排在功能线的**第一位**；但它必须建立在绿色 CI 之上 —— 加密是唯一会同时改动握手、连接管理、传输三条主链路的改动，在"测试基线是红的、且没人自动跑测试"的状态下做它，风险与收益不成比例。

### T3 的技术选择（建议：选项 B）

`发现协议设计书.md:540-549` 给了两条路：

- **A 保留优化**：给 `DiscoveryApp`/`PeerApp` 一个 epoch 递增端口（现在 `LocalEpoch func() uint64` 是只读的），在 `Upsert` 新条目、`MarkOffline`、BYE 处理处 bump。
- **B 取简法（推荐）**：`HandlePeerListReq` 忽略 `list_epoch`，永远返回全量。200 节点下一次响应约 12.8 KB、每节点 5 分钟一次 ⇒ 单种子出站 < 2 KB/s，与 ADR-011 的核算结论一致，**且没有正确性风险**。

推荐 B 的理由：A 会引入一个"目录变化 → 递增"的跨模块信号，正是本仓已经吃过两次亏的"多处真相"形态（见 T6）；而 B 把一条容易腐化的优化换成一条恒定正确、成本可忽略的行为。若日后节点数增长到需要它，再按 ADR-010 的复评条件（`ADR-010:43-44`）重新引入。

## 3. 版本路线

### 3.1 v1.1 — 安全与规模化（3–4 周）

**主题**：兑现架构书 §9.1 选项 C 的后半段（"先 A 后 B"里的 B），并把群聊从"能用"提到"够用"。

| 范围                      | 说明                                                                                                                                                                                                  | 量  |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- |
| **Noise_XX 端到端加密**   | 新增 `internal/adapters/net/noise`；`FlagEncrypted` 真正生效；`security.encryption = off \| prefer \| require` 三档真正被消费（现在只存不读）；用 capability 位做灰度，两端都支持才升级，否则回落明文 | L   |
| **指纹校验 UI（TOFU）**   | 首次连接展示节点指纹让用户确认，指纹变更时**显式告警**而不是静默继续；需要一张本地信任表（新迁移 v5）。这是防 MITM 的最后一环，也是加密上线后唯一有意义的用户可见安全交互                             | M   |
| **密钥轮换 + 拉黑**       | `StateBlocked` 已有领域与 DB 支持但从无代码设置它 —— 补上"拉黑节点"这条真实能力（拒绝握手 + 从目录剔除）；密钥轮换需要定义旧 key 的失效与信任迁移规则                                                 | M   |
| **群聊 20 → 50**          | 扇出改并行（已有 `max_dial_concurrency`）+ 连接复用；群上限提升必须同时给出"扇出成功率"与"峰值连接数"的验收数（对应 `max_active_conns=32` 的硬上限）                                                  | M   |
| **Gossip 成熟化**         | 退避、条目上限、epoch 语义收尾 —— 是 >50 人群的前提                                                                                                                                                   | M   |
| **群文件 / 群文件夹传输** | 后端协议与传输层**已经具备**，只差前端放行与聊天卡片接线。这是本版性价比最高的一项：用户会立刻感知，成本远低于加密                                                                                    | M   |

**明确不做**：中继（永久）、离线成员消息暂存扩到 24 h 以上、群主离线自动选举（`ADR-003:33-34` 已明确不做）。

**验收标准**：

1. 启用 `encryption = require` 后，tcpdump 抓包**读不出**聊天正文与文件名；
2. 一端 `off` 一端 `require` 时，双方给出明确失败原因而不是静默降级；
3. 伪造指纹（对端换 key）时用户收到告警，且必须显式确认才能继续；
4. 50 人群扇出：一次发送的送达率、峰值并发连接数、发送完成耗时可测；
5. 群里发一个 1 GB 文件，能续传、能取消。

**所需 ADR**：ADR-013（加密通道选型与降级策略）、ADR-014（TOFU 信任模型与指纹变更处理）。

### 3.2 v1.2 — 体验闭环（3 周）

**主题**：把"聊天工具该有的日常功能"补齐。这一版的每一项都是用户每天会碰到的，且多数是**纯前端工作量**。

| 范围             | 现状与说明                                                                                                                                                                                                             | 量  |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- |
| **消息历史分页** | **后端已经支持游标**（`ChatService.History(peerID, limit, before)`，`services.go:533`），前端却硬编码 `limit: 100, before: 0`（`chat.ts:120-125`）—— 即"翻不到更早的消息"。这是本版最便宜的一项                        | S   |
| **消息全文检索** | 现在搜索**只覆盖联系人与群**，不覆盖消息（`ContactPanel.vue:50-56`）。落地前需先验证 `modernc.org/sqlite` 的构建是否启用了 FTS5（这是**待验证项**，不是已知结论）；若不可用，退化为按会话内 `LIKE` 检索 + 时间范围过滤 | M–L |
| **群成员管理**   | `GroupService.AddMember` 与 `stores/group.ts` 的 `addMember` **都存在但从未被任何组件调用** —— 群只能创建，不能加人/移除/改名/退出/解散。补 UI + 补齐后端缺失的移除/改名/退出（成员变更走既有的 epoch + 群主签名机制） | M   |
| **消息操作**     | 复制 / 引用回复 / 转发 / 本地删除，目前 `ChatBubble.vue` 连右键菜单都没有。建议先做"复制 + 引用回复"（改动小、收益直接），转发与删除放第二梯队                                                                         | M   |
| **长列表性能**   | 消息、传输列表、调试流都是裸 `v-for`，无虚拟化；调试流靠"超过 500 条丢历史"兜住。历史分页做完后，消息列表的虚拟化就是必需项而不是优化项                                                                                | M   |
| **交互可达性**   | 联系人行是 `<div @click>`，**无 `tabindex`/`role`/键位处理，键盘完全不可达**；若干图标按钮缺 `aria-label`；正文字号 13px 偏小（`style.css:147-152`）                                                                   | S–M |
| **拖拽范围**     | 拖拽只在聊天面板内生效，丢到别处**静默无提示** —— 至少给一个落点高亮或提示                                                                                                                                             | S   |
| **i18n（可选）** | 全量硬编码中文、`index.html` 固定 `lang="zh-CN"`、无 `vue-i18n`。若无非中文用户需求，**建议明确不做**，不要半途引入                                                                                                    | L   |

**明确不做**：Markdown/富文本渲染（当前 `white-space: pre-wrap` 纯文本是刻意的安全选择，引入 `v-html` 需要先解决 XSS 面）；消息编辑（会与 `msg_id` + ACK 的不可变语义冲突）。

**验收标准**：向上滚动能连续加载到会话第一条消息且不卡顿；搜索能在 1 s 内从 1 万条消息里命中；能建一个群、加 3 个人、踢 1 个人、改名、退出，且所有成员看到一致的 epoch；仅用键盘能完成"选联系人 → 发消息 → 翻历史"。

## 4. 贯穿全程的工程基建与规模验证

这一轨道不单独占版本，而是**每个版本都必须交付**的部分 —— 它直接对应你选的"工程基建与长期可维护性"。

### 4.1 已声明但从未验证的 SLO

架构书 §2.1 的质量属性表里，有几条**至今没有任何测量**：

| SLO      | 目标                            | 现状                                                                                                                     |
| -------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 性能     | 千兆 LAN 单文件 ≥ 80 MB/s       | **从未测过**。现有 e2e 只验证"传得对"，不验证"传得快"                                                                    |
| 规模     | 全局 ≤ 200 节点                 | 只测到 **20 节点**（`test/scale`）。200 节点下"常驻连接 0""目录 200 条收敛""`max_active_conns` 不被打爆"都是推断而非事实 |
| 可测试性 | 领域层覆盖率 ≥ 80%              | 有 `make test-domain-cover` 目标，但**没有门槛**，CI 不会因覆盖率下降而红                                                |
| 可靠性   | 消息 at-least-once + 去重       | 有幂等用例，但**没有真实网络抖动/杀连接**下的验证（混沌测试缺失）                                                        |
| 可维护性 | 新增一种消息类型 ≤ 3 个文件改动 | 无度量方式，建议在 v1.1 加密（新增一个消息类型族）时顺便记录实际改动面                                                   |

**建议**：S1 先补 `test/chaos`（随机杀连接、随机丢包、随机延迟）并入 CI；200 节点 soak 与吞吐基准放在 v1.3（并发调度改动前后各测一次，才有对照意义）。

### 4.2 架构红线的执行力

`make lint-arch` 目前只检查 R1（domain 禁 import）与两条极窄的 R2/R3 模式（`Makefile:41-45`）。R2 真正的语义是"适配器之间禁止互引"，当前只检查了 `adapters/net` 不引 `adapters/store` 一条路径。建议在 T2 的 CI 里把它扩成"适配器之间任意互引都报错"的通用规则 —— 否则"红线"会继续停留在"靠自觉"。

### 4.3 本仓的工程纪律（建议原样继承）

本仓做得好的地方应当写进新计划，避免后续用别的方式做：

1. **先设计文档 → 再 ADR → 再实施计划 → 再验收测试**，每个 Task 一次提交（可回滚锚点）。
2. **新协议动作必须先立 ADR**（本次从 ADR-012 起编号）。
3. **验收标准要写成可执行测试，而不是手工清单** —— 这是一条用代价换来的教训：文件夹传输的九条双实例手工验收、离线传输 v2 的四条验收，**至今没有执行过**（`folder-transfer.md:1746` 自述）。能被自动化的一律自动化；确实需要人眼的（配色、对齐、真机观感）在计划里单列"人眼验收"并指定执行者与时间。
4. **`FakeClock` + 内存适配器是测试必需品**：心跳/TTL/空闲回收/退避都必须可确定性测试。
5. **前端事件监听必须节流**（进度类 4–10 Hz）—— 已有实现，别在新面板里漏掉。
