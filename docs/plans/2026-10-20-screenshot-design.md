# 截屏（本地单帧 + 交互式选区标注）设计

日期：2026-10-20
状态：设计已定稿（经多轮决策澄清），已实施
参照：`docs/plans/2026-10-20-screenshot.md`（实施计划）

## 1. 目标与非目标

**目标**：在聊天输入框上方提供「截屏」动作 —— 用户可以：

1. **交互式截屏（主力形态）**：点一下进入全屏遮罩，**鼠标拖拽框选一块区域**，
   再用简单的标注工具（矩形 / 箭头 / 画笔 / 文字 / 马赛克）把重点圈出来，
   确认后作为图片发给当前会话对方；
2. **整屏截屏**：一键抓下**本机当前显示器**的完整画面，
   并且可以选择**画面里是否包含蜂群自己的窗口**。

**为什么交互式是主力**：整屏截图里 90% 的内容是用户不想要的，
而「框一块 + 圈出重点」才是真实的意图。微信 / QQ / Snipaste 的交互
都是这一套，用户不需要学习成本 —— 拖一下、圈一下、Enter。

**为什么只做「本地自截」**：截屏这件事本身没有歧义（本地截图发给别人），但一旦允许
**对端远程触发本机截屏**，它就变成了无声的远控能力 —— 需要授权、需要确认、需要审计。
本仓 PRD §4.2 明确把「远程控制 / 屏幕共享」列为不做（见
`docs/plans/2026-10-14-PRD差距与待开发清单.md:457`）。因此本设计把「本地单帧截屏」
与「远程控制 / 屏幕共享」划清界限：

| | 本设计 | 远程控制 / 屏幕共享 |
| --- | --- | --- |
| 触发方 | **本机用户**点击 | 对端发起 |
| 画面 | **单帧静态图** | 连续流 |
| 协议 | **不新增任何帧** | 需要新增流控帧 |
| 授权 | 无（本地动作） | 需要确认机制 |

**非目标**：活动窗口截图、多显示器拼接（多屏可以**各自选区**，但不会拼成一张图）、
连续屏幕共享、对端远程触发的截屏、截屏历史记录、截屏另存为本地文件
（对端图片消息的「另存为」已由 `ImageLightbox` 提供）。

## 2. 用户流程

```
① 用户在聊天输入框上方点「截屏」
   ├─ 点主键  → 用【上次用的模式】直接截（默认：交互式）
   └─ 点 ▾     → 弹菜单三选一：
                 · 交互式截屏（框选 + 标注）  ← 主力
                 · 截屏（保留本窗口）        ← 画面里能看到蜂群界面
                 · 截屏（隐藏本窗口）        ← 画面里没有蜂群界面
② 交互式：Go 侧抓下所有屏幕 → 全屏变暗的覆盖层弹出
           → 用户拖拽框选 → 可选标注 → Enter 确认 / Esc 取消
   整屏：Go 侧直接抓「鼠标所在那块显示器」的画面
        （隐藏模式下：把本应用的窗口从捕获中排除）
③ 图片压缩 → 落进输入框上方的【草稿缩略图行】
④ 用户可以：直接点发送 / 「×」丢掉 / 「重截」再来一张
⑤ 发送键把草稿作为图片消息发给当前会话（单聊或群聊）
```

**为什么截完先进草稿而不是直接发**：截屏是「一次误点就会发出去」的动作 —— 而聊天里
发出的内容无法撤回（本仓明确不做撤回，见 `ChatBubble.vue:252-255`）。先给用户看一眼，
是最便宜的一道防线。注意这与既有的「Ctrl+V 粘贴图片直接发送」（`ChatView.vue:414`）
不同：粘贴是用户已经明确选中了剪贴板里的图，截屏则可能是误点。

### 3.1 工具栏按钮（`views/ChatView.vue` 的 `.tools`）

```
┌───────────────────────────────────────────────┐

│              └─┬─┘                          │
│                ▼                             │
│         ┌────────────────────────┐           │
│         │ 交互式截屏（框选 + 标注）│  ← 默认  │

│         │ 截屏（隐藏本窗口）      │           │

└───────────────────────────────────────────────┘
```

- **主键 + 下拉箭头**而不是两个并列按钮：模式是「上一次的选择」，多数时候用户不想
  每次都做选择；并列两个按钮会把「默认用哪个」这个信息推给用户自己想。
- 下拉菜单复用 `EmojiPicker` 的定位思路（`.emoji-wrap` + 绝对定位弹层）。
- 禁用条件与其它工具一致：没有会话 / 群已解散 / 设置里关掉了「允许截屏」。


- 缩略图最大 88×56，圆角，`object-fit: cover`。
- 草稿存在时，**文本输入框仍然可用** —— 截图和打字是可以并存的两件事。
- 「重截」保留当前模式，直接再抓一张（覆盖草稿）。
- 发送键的可用条件从「有文字」放宽为「有文字 **或** 有草稿」。

### 3.3 发送语义

草稿与文本**不互斥**：按发送时先发图片、再发文本（若文本非空），即两条消息。
这样「截了张图，顺便写一句『看下这个』」是自然的操作。

### 3.4 交互式截图：覆盖层 + 选区 + 标注

这是本功能的主力形态，也是与「一键整屏截图」最本质的区别：
**用户看到的是「抓屏那一刻的静态画面」，不是实时桌面**。

#### 3.4.1 为什么用「独立覆盖层窗口」而不是在主窗口里画

覆盖层必须是**独立的无边框置顶窗口**，铺满目标显示器：

- 主窗口做遮罩 → 主窗口的位置和大小限制了遮罩范围，铺不满整块屏；
- 更要命的是「遮罩自己会入镜」：把主窗口藏起来再画遮罩，等于**先拍一张照再画**。

所以流程必须是 **先抓屏 → 再开窗**，底图随会话一起下发（见 §4.5）。

#### 3.4.2 坐标：物理像素位图 + DIP 布局

| 东西 | 单位 |
| --- | --- |
| Canvas 位图（底图） | **物理像素** |
| CSS 布局（工具栏、选区框） | **DIP** |
| 鼠标事件坐标 | DIP → ÷ scaleFactor → 物理像素 |

三套坐标混用是这个功能最容易出错的地方。之所以要引入 `scaleFactor`：
150% 缩放的屏幕上，一个 DIP = 1.5 个物理像素，标注线的粗细、箭头的长度
如果不换算就会在高分屏上「细一半 / 短一半」。

#### 3.4.3 遮罩用「四个矩形」而不是挖洞

选区外的区域用 4 个矩形围出来（上下左右），**不用**
`globalCompositeOperation = 'destination-out'` 在遮罩上挖洞。
后者会让选区直接露出**实时桌面**（而不是抓屏那一刻的画面）——
选区里出现一个正在动的鼠标指针或弹窗，用户会以为是截图 bug。

#### 3.4.4 标注工具

| 工具 | 交互 | 说明 |
| --- | --- | --- |
| 矩形 | 拖拽 | 画一个空心框，用来圈重点 |
| 箭头 | 拖拽 | 带箭头的直线，指向要说明的位置 |
| 画笔 | 自由拖拽 | 折线，用于圈涂 / 打勾 |
| 文字 | 点击 | 弹浮动输入框，回车落字 |
| 马赛克 | 拖拽 | 打码，遮住隐私信息 |

- **选区**不是一种工具：任何时候按住左键拖动都是在**重新框选**；
  工具栏上的「⛶ 整块屏幕」按钮等价于「不框选，直接要整屏」。
- 颜色：红 / 黄 / 绿 / 蓝 / 白 **五色**；线宽固定 3（画布是物理像素坐标）。
- **马赛克的实现**：把该矩形区域「缩小再放大」并关掉插值
  （`imageSmoothingEnabled = false`），得到像素块效果。真打码需要后处理，
  前端这样做的代价是**可被反推**（适合「顺手遮一下」，不适合「安全遮蔽」）。
- **撤销**：`Ctrl+Z`。

#### 3.4.5 快捷键

| 键 | 作用 |
| --- | --- |
| `Esc` | 取消整次截屏 |
| `Enter` | 完成（选区 + 标注都定了） |
| `Ctrl+Z` | 撤销上一步标注 |

#### 3.4.6 导出：逐档降质以满足 512KB 上限

前端把「选区裁剪 + 标注」合成到一张离屏 Canvas，再导出 JPEG。
为满足协议上限 512KB，按 `quality = [0.92, 0.85, 0.75, 0.65, 0.5]` ×
`scale = [1, 0.85, 0.7, 0.55, 0.4]` 逐档组合尝试，**取第一个 ≤460KB 的结果**
（留 52KB 余量给 base64 与后端处理）。

后端仍然会再校验一次（`CommitOverlay` 拒收 >512KB 的图）。

## 4. 后端设计

### 4.1 分层落点

| 层 | 位置 | 职责 |
| --- | --- | --- |
| domain | `internal/domain/ports/ports.go` | `ScreenCapturer` 接口 + `ScreenImage` / `Display` 值类型 + 模式常量（**零 I/O**，符合红线 R1） |
| adapter | `internal/adapters/screencap/` | 各平台抓屏实现（`screencap_windows.go` / `_darwin.go` / `_linux.go` / `_other.go`） |
| adapter | `internal/adapters/wails/screenshot_service.go` | 整屏抓屏：模式判定 → 抓屏 → 压缩 → 出 base64；`SendDraft` 投递草稿 |
| adapter | `internal/adapters/wails/screenshot_overlay.go` | 交互式截图：会话状态 + 6 个服务方法 + `OverlayHost` 接口 |
| adapter | `internal/adapters/wails/overlay_wails.go` | `OverlayHost` 的 Wails 实现（开窗 / 关窗 / 焦点 / 发事件） |
| 组合根 | `main_wails.go` | 装配 `screencap.New()` 与 `NewWailsOverlayHost()` → `wails.Deps` |

**为什么覆盖层能力要再抽一层 `OverlayHost`**：`ScreenshotService` 需要「开一个窗口」，
但那是桌面壳层的职责。直接让服务层持有 `*application.App` 会把 Wails 运行时
带进服务层（也就带进了它的测试）。抽出 5 个方法的小接口，服务层就能在
**没有 Wails 运行时**的环境里被测试。

**为什么不放在 `internal/infra/`**：`infra` 里放的是「与业务无关的纯计算/格式适配」
（如 `imagecodec`）。抓屏是**平台适配器**（要调系统 API），放 `adapters` 更贴切。
但要注意红线 R2（适配器之间禁止互引）—— 因此 `wails` **不能** import `screencap`，
必须经由 `ports.ScreenCapturer` 接口 + 组合根注入。

**为什么不放 `internal/app/`**：本功能不涉及任何业务规则、没有跨用例编排、
没有领域状态。它就是「一个系统能力的门面」，走 adapter → service 直通即可。
硬塞进 app 层只会造出一个只有一行转发的方法。

### 4.2 接口

```go
// ScreenImage 是一张抓到的屏幕图像（像素数据，尚未编码）。
type ScreenImage struct {
    Width, Height int
    Data          []byte // RGBA8888，长度 = Width*Height*4
}

// Display 是一块显示器在虚拟桌面上的位置与尺寸。
//
// 三套坐标必须同时给出：
//   X/Y/Width/Height                —— DIP（虚拟桌面布局，给窗口定位）
//   PhysicalX/.../PhysicalWidth/... —— 物理像素（给抓屏与精确摆窗）
//   ScaleFactor                     —— 两者之比（鼠标坐标换算用）
// 虚拟桌面允许负坐标：副屏摆在主屏左边时 X 就是负的。
type Display struct {
    Index int
    X, Y, Width, Height             int
    PhysicalX, PhysicalY            int
    PhysicalWidth, PhysicalHeight   int
    ScaleFactor                     float64
}

// ScreenCapturer 是「抓本机屏幕」这项平台能力。
type ScreenCapturer interface {
    // Capture 抓取【鼠标当前所在的那块显示器】的画面。
    //
    // excludeSelf 为真时，本应用自己的窗口不出现在画面里。
    // 实现必须保证：无论成功失败，都不留下任何永久性的系统状态
    // （Windows 的 DDA 属性是粘性的，忘了复位会让用户此后所有截图都拍不到蜂群）。
    Capture(ctx context.Context, excludeSelf bool) (ScreenImage, error)

    // Displays 枚举本机的所有显示器（给覆盖层窗口定位）。
    Displays() ([]Display, error)

    // CaptureDisplay 抓取【序号为 index 的那块显示器】。
    //
    // 按序号而不是按物理矩形：macOS 的 CoreGraphics 只能按 display ID
    // 抓整块屏（CGDisplayCreateImage 不支持任意矩形），按矩形抓会让
    // macOS 变成特例。
    CaptureDisplay(ctx context.Context, index int, excludeSelf bool) (ScreenImage, error)
}
```

**为什么用 `excludeSelf bool` 而不是传窗口句柄**：
句柄是平台专有的（Windows HWND / macOS CGWindowID / X11 Window），塞进 domain 接口
会让 domain 层认识 Win32 概念（违反红线的精神）。而「排除本应用自己的窗口」这个
**意图**是平台中立的，各平台自己枚举自己的窗口即可 —— Windows 走 `EnumWindows` +
`GetWindowThreadProcessId` 比对本进程 PID，macOS 走 `CGWindowListCopyWindowInfo` 按
`kCGWindowOwnerPID` 过滤，X11 走窗口树按 `_NET_WM_PID` 过滤。

**顺带的好处**：按「本进程的所有顶层窗口」排除，**托盘气泡（自建 hover tip）也一并
被排除**了 —— 它同样是本进程创建的窗口，逐个排除它只会多写一份白名单。

### 4.3 模式

| 模式常量 | 含义 | 传给适配器 | 走哪条路 |
| --- | --- | --- | --- |
| `interactive` | 交互式：覆盖层选区 + 标注 | `excludeSelf = true` | `beginCapture` |
| `keep_window` | 画面保留蜂群窗口 | `excludeSelf = false` | `capture` |
| `hide_window` | 画面排除蜂群窗口 | `excludeSelf = true` | `capture` |

前端只传这三个字符串之一；非法值一律按「上次用的模式」处理、再兜底为
`interactive`，并记一条日志（前端是本仓的一部分，但仍不假设它不会传错 ——
一个拼错的模式不该让功能变成黑图）。

`interactive` **不走** `capture` 这条整屏抓取的路 —— 它需要的是
「先抓、再开窗、再裁剪」，与整屏抓取的时序正好相反（见 §3.4.1）。
服务端对 `Capture("interactive")` 直接报错，避免调错时给出「整屏图」这种半吊子结果。

**交互式为什么也排除本应用窗口**：覆盖层铺在屏幕上时，蜂群主窗口出现在
被选区域里没有任何意义 —— 用户要的是屏幕上的**别的**东西。所以
`interactive` 与 `hide_window` 一样按 `excludeSelf = true` 走。

### 4.4 压缩策略

抓到的原始像素是**物理像素**（4K 屏 = 3840×2160×4 ≈ 33MB）。这条路径上要编解码三次：

```
屏幕像素 (RGBA)
  → jpeg.Encode(q=92)          ← 一次有损编码，得到 ~1-2MB
  → imagecodec.Prepare(raw, 1920, 480KB)   ← 缩到最长边 1920 + 压到 ≤480KB
  → base64                     ← 进 IPC
```

**为什么自己先编一次 JPEG**：直接喂 PNG 给 `imagecodec.Prepare` 会有一个坑 ——
`Prepare` 对 PNG 是「体积达标就原样保留」（`imagecodec.go:109-114`），它**只看字节数、
不看尺寸**。一张 400KB 的 2560×1440 PNG 会被原样保留，绕过 1920 的尺寸上限。
自己先编成 JPEG，`Prepare` 的行为就确定了：合规则原样复用，不合规则缩放 + 按质量阶梯降质。

**为什么上限是 1920px / 480KB**：接收侧的内联图片上限是 512KB
（`internal/domain/message/inline_image.go:14` `MaxInlineImageBytes`）。
**这个上限本次不动** —— 它是协议/存储面的约束，动它意味着新旧版本之间的兼容面要重新谈。
480KB 留了 32KB 余量给 base64 前后处理。

**为什么 1920 而不是现成的 1280**：`imagecodec.DefaultMaxEdge = 1280` 的取值理由是
「聊天窗口里放大后仍然清晰」—— 那是对**用户自己选的图片**说的。截屏的内容常常是
要给人看**细节**的（报错信息、代码、表格），1920 是一张 1080p 屏的原生宽度，
再小就真的会看不清。

### 4.5 交互式覆盖层：时序、会话与接口

**时序（顺序不可换）**：

```
用户点「截屏」
  → beginCapture()
      ① 枚举显示器
      ② 逐块抓屏（DDA 排除本应用窗口）→ 每块存一张 JPEG
      ③ 每块屏开一个覆盖层窗口（隐藏状态）
  → 覆盖层窗口加载完成 → getOverlayImage(i) 取本屏底图
  → 画好第一帧 → overlayReady(i) → 显示窗口
  → 用户框选 / 标注
  → Enter → commitOverlay(base64, w, h)
      ④ 后端校验（≤512KB、魔数嗅探、尺寸有效）
      ⑤ 关闭全部覆盖层窗口
      ⑥ Emit("screenshot:ready", dto) → 主窗口收下，落到草稿行
```

**为什么底图要走一次「回头取」而不是随 `beginCapture` 返回**：
`beginCapture` 的返回值是给**主窗口**用的（主窗口需要知道有几块屏），
而底图只有**覆盖层窗口自己**需要。所以底图存进服务端的会话里，
由覆盖层窗口自己来取 —— 也避免了几 MB 的 base64 在两个窗口之间白跑一趟。

**为什么「显示窗口」要等前端说准备好了**：WebView 首次加载 + 首帧渲染要
一两百毫秒。窗口一创建就显示，用户会看到一块白屏在屏幕上闪过去。
所以窗口建成时是 `Hidden: true`，前端画完第一帧才调 `overlayReady` 显示。

**接口**（`ScreenshotService`，全部走已有的 Wails 绑定机制）：

| 方法 | 作用 |
| --- | --- |
| `BeginCapture() (OverlaySessionDTO, error)` | 抓屏 + 开覆盖层，返回显示器清单 |
| `GetOverlayImage(index) (OverlayImageDTO, error)` | 覆盖层取本屏底图（base64 JPEG） |
| `OverlayReady(index) error` | 「我画好了，显示吧」 |
| `FocusOverlay(index) error` | 把键盘焦点抢到本屏覆盖层 |
| `CommitOverlay(dataB64, width, height) error` | 提交结果 → 事件回主窗口 |
| `CancelOverlay() error` | 放弃本次截屏 |

**跨窗口回传**：结果不走「主窗口轮询」，走**事件**（`screenshot:ready`）。
主窗口订阅它，把结果放进草稿。
选区裁剪与标注都在前端 Canvas 完成 —— 同一套代码在三个平台通用，
后端不需要知道「什么是箭头」。

**多屏的键盘焦点问题**：多屏时每块屏一个窗口，键盘焦点只在其中一个上。
用户在 A 屏拖拽、焦点却在 B 屏时，Esc / Enter 会打空 —— 表现为「按了没反应」。
所以前端在**第一次鼠标按下**时调 `focusOverlay(displayIndex)` 把焦点抢回来。

**为什么覆盖层能力要抽成接口（`OverlayHost`）**：开窗 / 关窗 / 发事件这三件事
都是桌面壳层的职责。抽成接口后，服务层可以在**没有 Wails 运行时**的环境里被测试
（换个假实现即可），而不必把 `application.App` 引进服务层 —— 这也守住了
「domain 不依赖 adapter、adapter 之间不互引」的红线。

### 4.6 「已压缩图片」通道

**这是实现阶段发现并补上的一环，原设计没写。**

问题：草稿最终要变成一条图片消息，而图片消息的通用发送路径
（`ChatService.SendImageBytes` → `prepareImageData` → `imagecodec.Prepare`）
会用**默认上限**（1280px / 300KB）再压一次。截屏在抓屏那一刻已经按
1920px / 480KB 压过了，再走那条路就等于把它压回 1280px —— 4K 屏的截图
会糊掉一大截，而这恰恰是截屏最不该损失的东西。

解法：新增一条**只做校验、不做压缩**的发送通道
（`ScreenshotService.SendDraft` → `preparePreparedImage`）：

- 保留的校验与通用路径**完全一致**：魔数嗅探（不信调用方给的 mime）、
  体积不超过接收侧上限（`message.MaxInlineImageBytes` = 512KB）。
- 唯一的区别：不缩放、不重编码。
- 产出的仍然是同一套 inline image 消息格式，**对端与旧版本完全兼容**。

如果不做这一环，最省事的做法反而是把截屏的压缩上限也降成 1280/300KB
—— 那样能少写一个方法，但用户拿到的是一张 1280 宽的截图。

### 4.7 各平台实现

#### Windows（`screencap_windows.go`，主平台）

1. `GetCursorPos` → `MonitorFromPoint(pt, MONITOR_DEFAULTTONEAREST)` →
   `GetMonitorInfoW` → `rcMonitor`（物理像素矩形）。
2. `GetDC(NULL)` 取屏幕 DC → `CreateCompatibleDC` → **`CreateDIBSection`** →
   `BitBlt(SRCCOPY)` → 直接读 DIB 段的像素内存（BGRA → RGBA）。
   - **为什么不用 `CreateCompatibleBitmap` + `GetDIBits`**：`GetDIBits` 从 DDB
     取像素时对「hdc 与位图的对应关系、位深、上下方向」的组合很挑，失败时
     `GetLastError` 常常返回 **0** —— 看起来像参数错又不像，极难定位
     （实施时真在这上面卡住过）。`CreateDIBSection` 的像素内存是系统直接给的，
     `BitBlt` 完就能读，零中转、零这类坑。
3. **DPI**：抓屏前把当前线程切到 `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2`
   （`SetThreadDpiAwarenessContext(-4)`），抓完恢复。**必须做** —— 进程若不是
   per-monitor DPI aware，`GetDC(NULL)` 的坐标会被系统虚拟化，而 `GetMonitorInfo`
   返回的是物理像素，两者对不上，截出来的图会「错位一半」。混合缩放（150% + 100%）
   的机器上这个错位最明显。
4. **排除窗口**：`EnumWindows` 枚举本进程顶层窗口 → 逐个
   `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`；`defer` 里全部复位为
   `WDA_NONE`。
   - `WDA_EXCLUDEFROMCAPTURE`（0x20）需要 Windows 10 2004（build 19041）以上。
   - 老系统降级为 `WDA_MONITOR`（0x01）：窗口在捕获里显示为黑块 —— 不是「不出现」，
     但视觉上「没有本窗口内容」这个诉求仍然成立。
   - **DDA 是粘性的**：这是本设计里最容易埋雷的一条。忘记复位 = 用户此后用任何工具
     截图都拍不到蜂群窗口，而且没有任何报错提示他去找原因。

#### macOS（`screencap_darwin.go`，cgo）

- `CGWindowListCopyWindowInfo` 取全部窗口 → 过滤掉 `kCGWindowOwnerPID == getpid()`
  的那些 → 剩下的 ID 列表交给 `CGWindowListCreateImage`（`kCGWindowListOptionOnScreenOnly`
  + 指定 ID 列表）→ 得到「不含本应用窗口」的合成图。
- 「鼠标所在显示器」用 `CGGetDisplaysWithPoint` 取包含光标位置的显示器。
- **cgo 是必须的**：CoreGraphics 没有纯 Go 绑定。build tag 为 `darwin && cgo`。
  这不破坏项目现有的纯 Go 构建 —— `darwin` 目标本来就只能在 macOS 上构建（需要 SDK），
  而 Windows / Linux 的构建不受影响。
- **首次必须用户手动授权屏幕录制**（系统设置 → 隐私与安全性 → 屏幕录制），
  未授权时 `CGWindowListCreateImage` 拿到的是**黑图而不是错误**。
  必须在 `Info.plist` 里声明 `NSScreenCaptureUsageDescription`。
  本设计**不**做「检测未授权并弹引导」（检测本身在 macOS 上不可靠），改由验收清单
  与首次使用提示覆盖。

#### Linux X11（`screencap_linux.go`）

- **X11 抓屏依赖 Composite 扩展**：没有它，`GetImage(root)` 拿不到子窗口内容
  （只得到根窗口的背景 pixmap）。所以「正确抓屏」这条路必须走 Composite。
- 走 Composite 之后，「排除本应用窗口」是顺带的：逐窗 `XCompositeNameWindowPixmap`
  抓取再按 Z 序合成，**跳过本进程拥有的窗口**即可。
- 显示器几何用 Xinerama / RandR 取「包含光标的屏幕」。
- **Wayland 根本做不到**：合成器不允许应用抓别人的屏幕（甚至抓自己的也有严格限制）。
  因此 Linux 平台的实现**只支持 X11**，`WAYLAND_DISPLAY` 存在时明确报错
  「当前是 Wayland 会话，不支持截屏」，而不是给一张黑图。
- 依赖：`github.com/BurntSushi/xgb`（纯 Go 实现的 X11 协议库）。选它是为了
  **不引入 cgo** —— 项目现在是纯 Go 构建，引入 cgo + libX11 会让 Linux 构建需要
  系统开发包，并失去交叉编译能力。

#### 其他平台（`screencap_other.go`）

编译期空实现 + 运行时明确错误「当前平台不支持截屏」。与项目现状一致
（托盘气泡、提示音也只有 Windows 实现）。

## 5. 配置

```toml
[screenshot]
# 允许截屏（总开关）。企业环境可能要求禁用本机截屏能力。
enabled = true
# 上次使用的模式：interactive | keep_window | hide_window。
# 决定「主键单击」的行为。默认 interactive（交互式是主力形态）。
last_mode = "interactive"
```

- `enabled` 默认 `true`。**不要**用 `if !c.Screenshot.Enabled { ... }` 之类的回填 ——
  `false` 是用户的合法选择，那样写会让「关掉开关」重启后自己打开
  （与 `config.go:130-134` 里 `Notify.Sound` 那个坑同一类）。
- `last_mode` 由 `ScreenshotService` 在截屏成功后写盘（只有用户**显式**通过菜单选过
  模式时才更新）。它**不**经过 `SettingsService.Save` —— 那是设置页的通道，
  两个写者会互相覆盖。

## 6. 提示与反馈

- **整屏截屏成功**：右下角轻提示「已截屏，已放入输入框」（复用 `ui.notify`）。
  为什么要有提示：截屏没有声音、没有窗口变化，用户按下之后如果画面没变化，
  会以为按钮坏了。
- **交互式截屏不需要成功提示**：覆盖层弹出来本身就是最强的反馈，
  交完之后草稿行也立刻出现在输入框上方。多一个 toast 只是噪声。
- **失败**：明确说原因，不用泛泛的「截屏失败」。已知失败原因与文案：
  | 原因 | 文案 |
  | --- | --- |
  | 设置里关掉了 | 「截屏功能已在设置中关闭」 |
  | 当前平台不支持 | 「当前平台暂不支持截屏」 |
  | Wayland | 「当前是 Wayland 会话，不支持截屏（切到 X11 桌面后可用）」 |
  | 取不到显示器 | 「没有找到可截取的显示器」 |
  | 抓屏失败 | 「截屏失败：<系统错误>」 |
  | 覆盖层打不开 | 「打开覆盖层窗口失败：<系统错误>」 |
  | 结果图过大 | 「截图结果过大（N 字节），超出单条图片消息上限」 |
  | 压不到上限内 | 「这张图太大了，压到能发出去的大小失败了」 |

## 7. 已知限制（写进文档，避免反复提出）

1. **macOS 未授权屏幕录制 = 黑图**（不是错误）。这是系统行为，不是 bug。
2. **Windows 锁屏 / UAC 安全桌面 / 登录界面 = 黑图**。安全桌面下普通进程无法抓屏。
3. ~~**DDA 对 GDI `BitBlt` 的效果必须真机验证**。DDA 主要在 DWM / Windows Graphics
   Capture 路径生效；历史上部分 Windows 10 版本上 `BitBlt` 仍能抓到被排除的窗口。~~
   **【已验证（2026-10-20，Windows 11）】**：在本机用一次性验证程序造了一个
   200×200 的纯红窗口，分别以「不排除」与「排除」抓屏统计画面中的红色像素：
   **不排除 = 30214，排除 = 590**。红色窗口确实从画面里消失了，
   因此「隐藏本窗口」在 Windows 上走 DDA 这条路是成立的。
   （残留的 590 个像素是窗口边缘/阴影等 DDA 未覆盖的部分，不影响「看不到本窗口内容」这个诉求。）
   验证程序是一次性的，已随本次改动删除。
4. **排除后那块区域显示的是「底下的内容」而不是黑块** —— 画面会有拼接感。
5. **鼠标所在屏按「点击那一刻」判定**。想截另一块屏做不到（需要多屏选择器，v2 再谈）。
6. **托盘气泡**与本应用其它窗口会一并被排除（这是好事，见 §4.2）。
7. **4K 屏截图压到 1920px 后会发糊**。这是 §4.4 的取舍：宁可发糊也不动 512KB 上限。
8. **本功能不记历史**。截出来的图只存在于草稿与消息里。
9. **macOS 与 Linux X11 的实现未在真机上验证过** —— 仓库的开发机是 Windows。
   - macOS 分支是 cgo + CoreGraphics，**在 Windows 上连编译都无法验证**
     （darwin 目标需要 macOS SDK）。代码是照着 CoreGraphics 文档写的，
     但「能编译」与「能跑」是两回事。
   - Linux X11 分支的**语法与类型**由交叉编译（`GOOS=linux go build`）保证，
     行为（Composite 逐窗合成的 Z 序、裁剪、坐标换算）没有真机验证。
10. **交互式模式下，蜂群主窗口**不会**出现在画面里**（同样走 DDA 排除）。
    与「保留本窗口」模式相反 —— 交互式是「我要截屏幕上的别的东西」。
11. **马赛克是前端做的「缩小再放大」**，像素块可以被反推。
    适合「顺手遮一下」，**不适合遮证件号 / 密码**。
12. **覆盖层窗口是本进程自己创建的窗口**，理论上可能被别的截屏工具拍到
    （它不在抓屏那一刻的画面里，只在屏幕上真实存在）。这是所有截屏软件的通病。
13. **多屏覆盖层只在 Windows 上做过定位修正**（`SetWindowPos` 用物理像素）。
    macOS / Linux 的窗口定位仍用 DIP 坐标，混合缩放多屏下**未验证**。
