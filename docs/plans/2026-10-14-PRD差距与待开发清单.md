## 0. 一页结论

**结论 1 —— 需求文档与代码的取向已经分叉，这本身是最大的一个"待办"。**
PRD 的 §4.2 与第十二章把「传输加密与身份认证」列为**本期不做**，前提是「Q3 内网可信、明文广播」。
而代码实际交付的是**更强**的基线：Ed25519 持久化身份 + 签名 ANNOUNCE + 三段握手认证 + 防重放
（`internal/adapters/net/tcp/handshake.go`、`internal/domain/identity`、`internal/adapters/keystore`）。
因此规格书里那些按"明文可信"写下的**必须项**（明文广播字段、无校验直接入目录等）**不需要做**，
需要做的是**把 PRD/规格书回写成与实现一致的版本**，否则后续每次对照都会产生一批假缺口。

**结论 2 —— 缺口不在"大功能"，而在"产品化的最后一公里"。**
FR-14 文件共享完成度最高（约 85%，端到端 + e2e），FR-01 发现层与 FR-13 群聊的后端相当扎实。
真正的空白集中在三块：
1. **上限与校验类**：单文件 10GB 上限、5000 字上限、接收前磁盘空间预检、自动重试上限 —— 前后端都没有；
2. **传输交互类**：速度/剩余时间 ✅（D-06）、暂停/恢复 ✅（D-07）、在途取消 ✅（D-08）、全局传输队列浮层 ✅（D-09）、发送与批量确认弹窗；
3. **界面骨架类**：左侧三 Tab、顶部发现状态灯、全局搜索、事件日志面板、免打扰。

**结论 3 —— 有 5 项是"通路已铺好、只差最后一步"，性价比最高，建议第一批做：**

| 项 | 差的那一步 | 证据 |

### 2.9 实施记录：D-01 / D-02（2026-10-14）

**D-01 单文件大小上限**

- 协议：`FileMetaAck` 增加 `reject` 字段，语义是**非空即拒收**。刻意不用 `ok bool`：JSON 缺字段解出来是零值，用布尔会让新发送端把**旧接收端**的「接受」读成「拒收」—— 一次升级打断所有传输。
- 接收端：`HandleFileMeta` 在**创建任何东西之前**判上限（`metaRejectReason`），超限就回带 `reject` 的 ACK 并直接返回：不落库、不建 `.part`、接收目录不留痕迹。
- 发送端：`HandleFileMetaAck` 里拒收分支**必须排在位图解码之前**（被拒时对端不带位图，`DecodeBase64("")` 会先报错，排在后面就永远走不到）；原因经 `chunkAck.reject` 送到发送协程，元数据阶段收到即失败；`shouldWaitForPeer` 用 `errPeerReject` 哨兵把它**挡在等待路径之外** —— 否则会变成一条永远转圈、且每次退避到点都重发一遍的任务。
- 配置：`transfer.max_file_size`，默认 10 GiB，`0` 表示不限制；边界用 `>` 而不是 `>=`（设 10GB 就该能发 10GB 的文件）。不需要在 `applyDefaults` 回填 —— `Load` 是先填 `Default()` 再解析文件，老配置文件天然拿到默认值。
- 界面：`SettingsDTO.maxFileSize` 已暴露给前端。
- **有意偏差**：文档写的「发送端前端在选文件/拖拽时拦截」推迟到 D-05。原因：前端此刻**拿不到文件大小**（选中文件只有路径，大小在后端 `stat`），而接收端的权威拒收已经把原因说清楚了；D-05 的确认弹窗本来就需要一个「发送前预览」接口，那时一并做前置拦截。
- 另注：上限是**每台机器自己的策略**。发送端不知道对端的配置，也不交换上限——真正的判定永远在接收端。

**D-02 接收前磁盘空间预检**

- 新增 `internal/infra/diskspace`：Windows 走 `GetDiskFreeSpaceEx`（取 `availableToCaller`，不是全卷空闲量，配额下更准），类 Unix 走 `statfs`（取 `Bavail`，不含 root 保留块）；**路径不存在时报错而不是回 0**（回 0 会被调用方读成「磁盘满了」，于是每次传输都被拒，而真实原因只是路径写错）。
- `ports.FileSink` 增加 `Root()`：`Create/CreateIn` 之前拿不到具体落点，而批次目录与根同卷，按根判剩余空间就够。
- 判定（`spaceRejectReason`）：`need = size - 已完成字节` —— 续传只补剩余，否则「磁盘刚好够补完」这种最该成功的情况会被自己误判成空间不足；**探测失败、未注入探测函数、目录条目、零字节**一律放行 —— 预检是提前止损，不是给传输新增一个拒绝理由。

**验证（本次实测）**：`go build ./...`、`go vet ./internal/...`、`go test ./... -count=1`（含 archtest 的 gofmt 闸门与三条依赖红线）、`go test -tags wails ./... -count=1` 全部通过。

## 2.10 实施记录：D-06（2026-10-15）

**速度 / 剩余时间（滑动窗口）**

- 新增 `internal/domain/transfer/rate.go`：`RateMeter`，定长样本环（32）× 5 秒滑动窗口，喂「累计完成字节 + 时刻」，吐 `Speed()`（字节/秒）与 `ETA(remaining)`。零值可用、无分配、只依赖 `time`（不碰 domain 零 I/O 红线）。
- **为什么滑动窗口而不是 EMA**：窗口有明确物理含义（「最近 5 秒的平均速率」），且停滞时行为天然正确 —— 没有新字节，旧样本滑出窗口，速率自动衰减到 0；EMA 不加「停滞检测」就会让旧速度永远挂在界面上。任务标题里的「EMA」按此兑现为等效的平滑能力。
- **速率口径**：发送侧用【已确认】字节（对端 ACK 过的块），不是「已发出」—— 发出去没确认的字节随时可能重传，算进速度会让界面虚高、ETA 变成谎言；接收侧就是【已写入】字节。新增 `chunkBytesDone` 按 `FileSize` 截断（最后一块通常不满，不截断时 4KB/1KB 块的文件误差 25%）。
- **采样时机**：在原有 `publishSendProgress`/`publishRecvProgress` 节流通过后各喂一个样本（默认 4 Hz），窗口 5 秒 ≈ 20 个样本；`TransferProgress.Speed/ETA` 字段、eventbridge 映射、前端 `speedText`/`etaText` 渲染原本就在，本次只补后端赋值，前端零改动。
- 防御分支（均有单测）：时钟回拨丢弃样本、累计值倒退重置（同 job 重试开了新任务）、`dt=0` 与样本不足时速率 0、`remaining<=0` 或速率未知时 ETA 0（前端对 0 的处理是不显示，而不是精度造假）。

**验证（本次实测）**：`go build ./...`、`go vet ./internal/...`、`go test ./... -count=1`（含 archtest 三条红线与 gofmt 闸门）、`go test -tags wails ./... -count=1`（含 e2e）、`go test -race ./internal/app/ ./internal/domain/transfer/` 全部通过。
新增 13 条用例：domain 侧 9 条（`TestRateMeter*`），app 侧 4 条（`TestSendProgressCarriesSpeedAndETA`、`TestRecvProgressCarriesSpeedAndETA`、`TestRecvProgressThroughChunkIngest`、`TestChunkBytesDoneClampsToFileSize`）。

## 2.11 实施记录：D-07（2026-10-15）

**暂停 / 恢复**

- **协议**：`TypeFilePause = 0x16` / `TypeFileResume = 0x17`（`internal/domain/protocol/const.go`，`TypeName` 同步），载荷 `FilePause{JobID}` / `FileResume{JobID}`（`wire.go`）。载荷**刻意只有 `job_id`**：方向由收帧方按自己持有的任务表解释（`job_id` 全局唯一），不放进帧里；也刻意没有 `reason` —— 暂停的原因只有一种（人点的），多一个字段就多一条「两端解释不一致」的缝。旧版本收到未知 Type 按规格 16.2 丢弃并计数、不断连，于是新旧混跑降级为「本地暂停」。
- **状态机**：`StatePaused` 的两条出路**不对称**（`internal/domain/transfer/state.go`）—— 发送侧 `paused → meta_exchange`（存量位图只是「对端 ACK 过的部分」，暂停期间对端可能已落盘更多块，**强制**重走 META 重协商），接收侧 `paused → transferring`（位图在接收方自己手里，直接续写即可）。`DBStatus()` 把 `StatePaused` 映射成 `paused`。
- **两本账**：`pausedByUser` / `pausedByPeer` 两个 map，不是一个布尔（`internal/app/transfer_app.go`）。一个布尔会出现两种错：对方按着时我一恢复它就自己传起来（覆盖对方意图）；或我按的暂停被对方的恢复信令悄悄解掉。数据路径的唯一判据是 `isJobPaused`（两本账，自带互斥），**不是** `recvJob.job.Status` —— `recvJob`（含 job 快照与位图）归会话读协程独占，跨 goroutine 读写会 `-race`，写更会把读协程刚推进的位图覆盖成零（「一按暂停进度条归零」那条 e2e 回归）。
- **落库**：`ports` 新增 `SetJobStatus`（**只**改 status 列），sqlite / mem 两实现；暂停路径**不用** `UpsertJob` —— 调用方手里那份 `Job` 是内存快照，接收侧进度由另一条写入路径（`SaveBitmap`）推进，整行覆盖就等于「暂停一下，进度先归零」。
- **统一出口**：新增 `errJobPaused` 哨兵，与取消走 `sendFile` 同一个 defer 出口，但**不发** `transfer:error`（否则暂停的任务整行标红），且**不许**掉进「对端不可达 → 转等待」（否则自动重试会把暂停的任务又跑起来）。分支排在取消**之后**：两个信号同时到达时以取消为准（终态压过中间态）。
- **边界（有意不做）**：等待态（等对端上线 / 批次排队）**不接受**暂停 —— 那两条路已有取消与立即重试，暂停一条还没开始的任务只会造出第三种说不清的中间态，也压不住自动拉起。哈希窗口（大文件是分钟级，此时还没有 `sendJob` 可收信号）的暂停意图只记在两本账上，在「哈希结束、META 之前」那道检查里兑现。
- **重启后的陈行**：内存两本账已丢，但库里的行仍写着 `paused`。`HandleFileMeta` 回头查这一眼（`direction=recv` 且 `status=paused`）→ 照常回 `FILE_META_ACK`（发送方要靠它定位续传起点）再补一条 `FILE_PAUSE`；**不**走「拒收」—— 拒收是终态，会把对端任务直接判失败。
- **META 不能复活用户的暂停**：用户按过暂停的接收任务收到新 META 时，保留原任务与位图不动，回 ACK + 补 `FILE_PAUSE`，让对端一起停下。
- **信令是 best-effort**：暂停**不**为发一条「我要停了」去新建连接（代价与收益不成比例）；恢复允许兜底拨号（它要把对端叫醒），拨号上限 3 s（`signalTimeout`），不让按钮假死。发不出去的场景由后续 META 重传自然收敛。
- **RPC 与前端**：`wails/services.go` 的 `PauseTransfer` / `ResumeTransfer` → bindings → `frontend/src/api/{types,bindings,mock}.ts` → `stores/transfer.ts` 的 `isPaused` / `canPause`（判据与后端 `PauseJob` 对齐）→ `TransferList.vue` 的暂停 / 恢复按钮。前端**只认 `status` 一个值**，不另造本地标记：恢复时后端先发一条 `transfer:state` 把它翻回协商中，否则随后到达的进度事件会被「暂停中不接受进度」的护栏丢掉、界面卡死在「已暂停」。
- **有意不覆盖**：全局「全部暂停」属 D-09（全局队列浮层）。
- **过程中的一条修正**：读数据路径起初仍在看 `rj.job.Status`，于是接收侧「已暂停」却照旧写盘、照样校验（`transfer_pause_test.go` 挂了 4 条）。已统一到 `isJobPaused`（`HandleFileChunk` / `HandleFileDone` / `HandleFileMeta`）；替身 `stubTransferRepo.SaveBitmap` 也从空操作改成**真实语义**（位图 + 已完成数写行），否则「暂停不能把进度冲掉」的断言永远看不到进度、只能靠改被测代码迁就。

## 2.13 实施记录：D-09（2026-10-15）

**全局传输队列浮层**

- **纯前端，没有新接口**：四个数字都在前端算 —— 速率只随 `transfer:progress` 事件到达（落库的 DTO 里根本没有速率），后端没有「整队速率」这个可查的量；而未结束的任务又总在列表窗口前列（`ListRecent` 按 `updated_at` 倒序取 50 条，正在跑的每条 ≤2 秒刷新一行）。因此这里的口径与用户在列表里看到的**完全一致**，加一个后端聚合接口只会多一份可能分叉的真相。
- **只在有未结束任务时出现**，没任务时一条屏幕都不占。判据用 store 里的 `activeJobs`（左栏角标同源），App 外壳靠**同一个集合**决定「底部留多少空间」—— 两处各算各的就会出现「留了空间却看不到浮层」或者反过来压住输入框。
- **`--queue-h` 是两者唯一的耦合点**（`style.css` 的布局尺寸段）：浮层高度与外壳的 `padding-bottom` 都读它，改高度不会出现「浮层长高盖住输入框」。轻提示默认贴底 30px，浮层出现时由 `.app.with-queue .toast` 抬到 `30px + --queue-h`，否则它正好落在浮层上。
- **总进度按字节加权**：不让「大文件 90% + 小文件 10%」各算一半；分母只算拿得到大小的任务（刚建出来的壳 `fileSize=0`，算进去会被 0 稀释）。进度线走 `transform: scaleX()` 而不是改宽度 —— 它每来一帧都要动一次，走 transform 不触发布局。
- **并发数写成 `N/M`**：N 是「正在传」的条数（判据就是后端 `PauseJob` 认的那两种状态），M 是设置里的全局上限。上限只约束**本机发起**的传输（接收侧由对端驱动），所以 N 理论上可能超过 M —— 这句写在 tooltip 里，而不是在界面上编一个更好看的数。
- **全部暂停 = 前端循环调用既有的 `pauseTransfer`**：后端 `PauseJob` 已经包含在途中断、对端信令与状态广播，这里只负责「对哪些任务、按什么顺序、失败怎么算」。串行而不是 `Promise.all`：一条一条来才对得上直觉，数量本来就受并发上限约束。
- **只暂停「正在传」的，与 D-07 划下的边界一致**：等待对方上线、批次排队中的还没开始跑，它们有自己的出口（立即重试 / 取消）。所以在一个文件夹批次里点它，停住的是此刻在传的那个文件，队列里下一个仍会照常开始 —— **要连队列一起停，得用批次卡片上的「全部取消」**。这条写进了按钮的 tooltip。
- **补了「全部恢复」**：规格只写了「全部暂停」，但一个只能单向停下的全局按钮会把用户送进死胡同（队里几条要一条条点回来）。同一套循环，单条失败静默跳过 —— 最典型的失败是「对方也按着暂停」，那时正确的动作就是什么都不做（对方恢复后会自动继续）。
- **浮层 `z-index: 90`，低于弹层的 100**：弹层打开时它不该浮在弹层之上；轻提示仍是 400。
- **预览模式（`api/mock.ts`）**：
  - 预置两条任务（一条「正在传」+ 一条「已暂停」）。理由与既有那条文件夹批次一样：浏览器里没有原生文件对话框，而浮层只在有未结束任务时才渲染 —— 不预置就永远走查不到。刻意**不挂模拟定时器**：浮层要验的是布局与文案，挂上反而会在三五秒内把它自己跑成 done，把要检查的形态跑没。
  - **顺手修掉一处会让走查说谎的缺陷**：`cancelTransfer` / `retryTransfer` / `pauseTransfer` / `resumeTransfer` 改的是夹具数组里的【原始对象】，绕过 store 那份响应式副本又不推事件，于是点下去界面要等下一次别的渲染才更新（表现为「点了没反应」）。四个动作现在都补上 `emit(EV.transferState, …)`，与真机「后端推状态事件」一致；`retryTransfer` 落的 status 也从 `active`（后端不存在这个值）改成 `idle`。

**验证（本次实测）**：`npm run typecheck`（vue-tsc）、`npm run build`、`go build ./...`、`go test ./... -count=1` 通过（`TestFileTransferResumesAfterInterruption` 仍是 §3.1 记的那条 Windows 不稳定项，单独重跑全过，与本次改动无关）。
界面部分在预览模式下用无头浏览器 + CDP 实测，不是只看代码：浮层高 44px 贴底、`z-index: 90`、外壳 `padding-bottom: 44px`、进度线贴在浮层顶边且宽度恰为 38%（`matrix(0.38…)`，与预置数据算出来的一致）、文案为 `3 个任务进行中 / 并发 1/3 / 6.4 MB/s / 38%`；点「暂停全部」后变成 `并发 0/3`、速率消失、按钮换成「全部恢复」、轻提示落在 `30+44=74px`（即确实被抬到了浮层之上）；深色与浅色两套主题各截一张确认对比度。

## 2.14 实施记录：D-10（2026-10-15）

**「续传自 XX%」展示**

- **新增一个字段，而不是复用已有的数**：`Job.ResumeFrom`（本次尝试的起点块数）+ `Job.ResumePercent()`（`domain/transfer/job.go:85,148`）。与 `Percent()` 的分工就是这个字段存在的全部理由 —— `Percent()` 读位图，一路上涨；`ResumePercent()` 读 `ResumeFrom`，写下就不动。界面上「续传自 12%」与「42%」同时出现，正是这两条问题各自的答案。若从位图现推，起点会随进度一起涨，用户看到的就是「续传自 42%」，等于没说。
- **必须落库（迁移 v8）**：`transfer_jobs` 加 `resume_from INTEGER NOT NULL DEFAULT 0`，沿用 v3–v7 的纯 `ADD COLUMN`、零重建。理由：重启一次、或换一次尝试（恢复 / 重试 / 退避后自动重发）之后，用户仍然要看得出「这条是从半截续的」—— 只放内存的话，同一份文件在列表里看起来就像从头传了一遍。默认 0 让历史行天然是「没有续传」，而不是乱猜一个起点。
- **写入时机只有两处，且各写一次**：
  - 发送侧在 `HandleFileMetaAck`（`transfer_app.go:551`）—— 对端回的位图就是本次的起点，落库之后不再动；
  - 接收侧在 `HandleFileMeta` 继承 `FindResumable` 位图时（`transfer_app.go:865`）—— 继承来的位图同样就是起点；新建任务的字段字面量不带它，保持 0。
- **为什么搭进度事件走**（`TransferProgress.ResumeFromPercent`，`payloads.go:73`）：起点是在 `FILE_META_ACK` 之后才定下来的，那一刻**没有任何事件**可用；而「收到状态变化就去重读整行」这条路会把界面盖回去 —— 发送侧的进度根本不落库（见 `sendFile` 的注释），重读拿到的是库里那份滞后的数。装配层（`eventbridge.go:212`）只在 `>0` 时放这个键：不续传的任务（绝大多数帧）一个字节都不多花。`TransferService.List()` 的 DTO 也带它（`resumeFromPercent,omitempty`），覆盖重启后的陈行。
- **前端三处**：类型与事件载荷（`api/types.ts`、`stores/transfer.ts`）；store 合并时**缺省沿用上一条**（事件只在真的续传时带它，抹成 `undefined` 会让「续传自 XX%」在传输途中因某一帧不带而一闪消失）；`TransferList.vue` 的 `resumeText()` 在文件名那一行渲染一个 tag，**不足 1% 不显示**（从 0.4% 接上的任务显示「续传自 0%」比不显示更让人困惑）。
- **预览模式预置 12% + 42%**（`api/mock.ts`）：浏览器里没有真实续传，不预置这颗标记永远走查不到。
