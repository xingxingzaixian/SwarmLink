# 2026-09-20 工作日志

## SwarmLink 架构设计（软件架构师视角）

**背景**：项目为无中心内网 P2P 聊天与文件分享工具（Go + Wails v3 beta + Vue3），原《设计书.md》为 v1.0 技术方案。

**产出**：`架构设计书.md`（约 1160 行）—— 架构评审 + 目标架构 + 协议 v2 + 数据模型 v2 + 8 条 ADR + 演进路线图 + 差异清单。

**核心结论（供后续会话直接复用）**：

1. **判断**：原方案的*技术调研合格*（UDP 广播的坑、modernc vs mattn、位图续传、原子替换、块三元组索引都选对了），但*架构缺位*（无依赖规则、无跨模块契约、P0 功能无设计预留）。

2. **5 个 P0 缺口**：
   - G1 群聊是 P0 但零设计（无 group 模型/扇出策略/成员同步）
   - G2 HELLO 不做认证 → NodeID 可任意冒充
   - G3 接收文件名未清洗 → 目录穿越写任意路径
   - G4 CHAT 消息不可靠（无 msg_id/ACK/outbox/去重）
   - G5 双向拨号无胜负规则 → 连接撕裂

3. **架构风格决策（ADR-001）**：六边形架构 + 事件驱动核心。四层：入站适配器 / 应用层 / 领域核心（零 I/O）/ 出站适配器 + infra（eventbus、clock、log）。`main.go` 为唯一组合根。
   - 三条红线：R1 `domain/**` 禁止 import net/database/sql/os/wails；R2 跨模块只走 ports 接口或事件总线；R3 适配器互不依赖。

4. **关键协议决策**：
   - 帧头扩为 Magic2+Ver1+**Flags1**+Type1+Len4（9B）+ 16MB 上限（ADR-006）
   - 三段式握手 HELLO/HELLO_ACK/AUTH，Ed25519 对转录 `H(域分隔 || nonce_A || nonce_B || pubKey_A || pubKey_B)` 签名（ADR-002）
   - 消息可靠性：msg_id(UUIDv7) + ACK + outbox，at-least-once + 幂等去重；**重复消息也必须回 ACK**（最易实现错的点）（ADR-004）
   - 传输：滑动窗口 W（初始 8，自适应至 64）+ 周期性**全量位图**回传（每 500ms 或每 32 块）替代累积 ACK；位图每 2s 或每 256 块批量落盘（ADR-005）
   - 群聊：全互联单播扇出，上限 20 人，群状态 owner 签名 + epoch 单调递增；数据模型按未来切 Gossip 的形状预留（ADR-003）

5. **破坏性数据模型变更（越早做越便宜）**：
   - `conversations` 主键 `peer_id → conv_id`（+ kind 字段）
   - `messages` 加 `UNIQUE(msg_id)` + state
   - 新增 outbox / peers / groups / group_members / schema_migrations

6. **架构关键简化洞察**：位图 = 256B/GB，回传成本可忽略 → 用"周期性全量位图"换掉累积 ACK + SACK 的复杂语义，是"用带宽换复杂度"的最佳交易。

7. **演进路线**：M1(3w 核心链路/立四层结构) → M2(3w 持久化与传输) → M3(3w UI，可并行) → M4(2w 硬化) = v1.0 约 11 周 → v1.1(4w 加密/跨网段) → v1.2(3w 吞吐/批量) → v2.0(6-8w 插件/多网络)。**明确不做**：微服务、消息队列、ORM、NAT 穿透、中心服务器。

8. **待用户决策的 4 项（已按 A/B/C 给出，含推荐）**：
   - 加密节奏：A 仅认证 / B 直接 Noise / **C 先 A 后 B（推荐）**
   - 群聊范围：**A v1.0 就上（推荐）** / B 推到 v1.1 但数据模型现在做 / C 伪群
   - 传输并发：A 保留 stop-and-wait / **B v1.0 就上滑动窗口（推荐）** / C 固定窗口 W=4
   - 规模假设确认：单网段 ≤200 节点、全局 ≤500、群 ≤20 人

**项目命名**：工作区目录为 `SwarmLink`，原设计书中占位名 `MyApp`/`myapp` 应替换。

## 补充：规模约束确认（用户回复"总节点应该在200节点以内"）

文档升级为 **v1.1**，新增以下内容（均已回写进 `架构设计书.md` 并加了修订记录）：

**新增决策**：
- **3.7 连接拓扑 + ADR-009「在线状态与传输连接解耦」**：原设计与 v1.0 都未说明节点间是否维护持久连接。决策为**不建立全互联持久连接**——原因是 200 节点全网 19,900 条连接会产生约 **1,300 pkt/s 的纯保活流量**（零用户价值），且网络抖动会触发 199 条连接同时重建的 **SYN 风暴**。改为：在线状态走 UDP announce，TCP **按需拨号 + 会话级保活 + 5 min 空闲回收**，单节点常驻连接目标 ≤10。
  - 代价：首条消息 +1 RTT 与一次握手（LAN <5ms，跨网段约 +60ms）；UI 必须区分"节点在线"与"连接可用"两种状态；群聊扇出需并发拨号（上限 8）。
- **ADR-010「全量节点目录同步，不做增量/分页」**：200 条 × ~64 B ≈ **12.8 KB**，一次响应发完，不需要版本向量/增量合并。

**被规模约束永久划掉的三项复杂度**（写进 8.7 的移除原因表）：
1. 分层/分区发现协议
2. **软中继（群聊方案 C）** —— 触发条件是"群 >200 人"，全局仅 200 节点，场景不存在
3. 目录增量同步 / 分片拉取

**群聊能力边界封闭**：20（v1.0）→ 50（v1.1）→ 200（天花板 = 全局节点数）。方案 C 永久移除，Gossip 即闭环。因此 9.2 选 A 的风险显著低于 v1.0 评估——**这就是终态架构，不需要留额外余地**。

**新增测试层级**：`test/scale` —— 单进程起 20~200 个虚拟节点跑发现与目录同步，上线前证明"200 节点不会打爆"。M1 完成标准已含此项。

**核心洞见（可复用于其他架构评审）**：架构的价值一半来自约束。一条明确的规模上限（≤200）比"可能几千节点"的模糊假设有价值得多——它一次性砍掉了三块复杂度，并让"按需连接"这个决策变得明显优于全互联。

**唯一剩余待确认项**：**200 个节点分布在几个网段？** 1~2 个网段无需额外机制；3~5 个建议随安装包分发默认种子清单；**10+ 个**则需"种子分发"机制——已在 9.5 明确警告：**只读引导节点极易演化成"事实中心节点"，若走这条路必须先界定边界（只发种子列表，不参与消息与文件路由），否则会侵蚀"无中心"这个核心卖点**。

## 补充二：拓扑约束确认（用户回复"3-5 个网段，手动维护，暂不考虑运维负担"）

文档升级为 **v1.2**（现约 1568 行）。核心新增：**4.5.1 跨网段发现** + **ADR-011**。

**方案（冻结）**：网段内 UDP 广播 + 网段间**种子单播拉取**。`PEER_LIST_REQ/RESP` 跑在单播上，与广播复用同一套协议。

**四条关键设计判断**（可复用于其他 P2P / 多网段方案）：

1. **种子不是服务器，是"配了更多种子地址的普通节点"** —— 零特权、零状态、可随时替换。种子与普通节点跑**同一套**目录交换协议，"特殊性"完全外置到配置文件。若接口里出现 `SeedClient.Relay` / `SeedServer.Authoritative` 之类方法，说明设计走形。
2. **每网段 ≥2 颗种子** —— 种子只是配置里的一个 IP，单颗失效会让该网段"对网段外消失"。3–5 网段 × 2 = 6–10 条 IP，手工维护可控。节点每轮**随机拉 2 颗**（不是全部），避免 200 节点打同一颗形成热点。
3. **不需要 `via` / `hop_count` / 来源标记即可防环** —— 两条规则：① 条目按 `node_id` 去重；② **TTL 用本地到达时间计，绝不用对端 timestamp**（跨网段时钟偏差不影响正确性）。因为新鲜度由接收方本地维护、不会被中转刷新，所以不存在陈旧条目回灌。**这是极易实现错的点。**
4. **跨网段进 M1，不进 v1.1** —— 它不是"以后要加的功能"，而是**发现协议报文的形状约束**。若 M1 按纯广播语义写死目录交换，v1.1 加种子要改协议；现在做只多 **2 天**。这是全文档"提前做最便宜"的判断。M1 完成标准随之加入**跨网段收敛用例**（单进程两个隔离 UDP 端口域 + 共享种子）。

**两条部署前置条件（网络侧事实，代码救不了，必须写进安装文档）**：
- **P-1**：任意两网段种子 IP 之间**可 TCP 直连**（三层可达，非 NAT 隔离）。不满足 → 跨网段全失效，**只能上中继**（架构级返工）。自检：启动时对种子做 TCP 探测。
- **P-2**：各网段**地址段不得重叠**（不能都是 `192.168.1.0/24`）。否则目录出现 `node_id` 不同、IP 相同的条目 → 跨网段寻址崩溃且**现象隐蔽极难排查**。自检：ANNOUNCE 携带 `subnet` 字段，**M1 就要加**。⚠️ "多厂区各自 192.168.1.0/24 + VPN 互联"是高频真实形态。

**被拓扑约束永久划掉的复杂度**：种子分发机制 / 只读引导节点；跨网段中继（**从"v2.0 可选增强"上调为"永久不做"**——P-1 成立则零跳数直拨，P-1 不成立是网络侧该修的问题）。

**成本核算**：复用 ADR-010 的 `list_epoch` 后，目录未变时返回空响应 → 单颗种子出站 **< 2 KB/s**，**种子机器不需要任何特殊规格**。

**两个新细节**：
- **种子必须固定 UDP 端口**（关掉 ADR-008 的端口回退）。第一跳走 UDP（带魔数探测包，种子**单播**回 ANNOUNCE），从 ANNOUNCE 学到实际 `tcp_port`/`node_id`/`pub_key`（带签名 → 种子身份第一跳即可验证），第二跳才 TCP 拨 `PEER_LIST_REQ`。
- **UDP 发现报文用独立魔数与独立编号空间**，不与 TCP 帧争用（UDP 需强魔数防误触，TCP 不需要）。`P2-6`"常量统一"修正为"常量**集中**但**不相同**"。

**数据模型调整**：`peers` 加 `subnet`，`last_seen` 明确为**本地到达时间**语义；`seed_nodes` 主键由 `node_id` 改为 `addr`（探测前根本不知 node_id），加 `tcp_port`/`last_epoch`。
**端口新增**：`SeedRegistry { Pick(n) []SeedAddr; Report(addr, learned, err) }` —— 注意接口里**不应**有 relay/authoritative 类方法。

**版本节奏变化**：v1.1 由"加密与跨网段"收窄为"**加密与扩容**"；到 v1.0 约 **11.5 周**（M1 +2 天）。

**剩余待决策**：仅 9.1 加密节奏 / 9.2 群聊范围 / 9.3 传输并发 三项。
